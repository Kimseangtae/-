# threads-watch: 스레드 레퍼런스에서 메소드를 뽑아 로빈님 사업에 적용

## 목적 (헷갈리면 이것만 기억)
- **하는 것**: 글이 말하는 방법론·원칙·사업 방식을 이해하고, 로빈님 사업의 어느 영역에 어떻게 적용할지 실행 과제로 바꾼다.
- **하지 않는 것**: 글의 훅·문장 구조·형식을 분석해 로빈의밥상 스레드 글로 베껴 쓰기. 이건 이 스킬의 일이 아니다.

## 로빈님 사업 지도 (적용 영역은 이 중에서 고른다)
| 코드 | 영역 | 지금 상태 요약 |
|---|---|---|
| A | 유튜브 채널 운영 (롱폼·쇼츠·라이브) | 구독자 약 21.5만, 55~70대 여성 핵심. "속지 않는 부엌" 철학 |
| B | 공동구매 | 정보 다큐 위장 90% 교육 + 자연 노출. 고정 댓글 → 키 콘텐츠 → 구매 퍼널 |
| C | 브랜드 콘텐츠·협업 제안 | 제안서 작성, 단가·조건 협상 |
| D | 멤버십·팬 관계 | 유튜브 멤버십, 커뮤니티 |
| E | 시간·업무 시스템 | 1인 운영. 기획·촬영·편집·글쓰기·CS 를 혼자 |
| F | 사업 확장 | 신규 채널, 상품, 강의, 오프라인, 팀 구성 등 아직 정하지 않은 영역 |
| G | 개인 성장 | 45세, 제주 거주, 러닝·필라테스. 셰프 20년 경력 |

## 실행 순서 (데스크톱 기준)

0. **재검토 대기 글 먼저 처리** (매 회 가장 먼저)
   ```bash
   python3 threads-watch/fetch_thread_full.py --pending
   ```
   답글을 못 읽고 분석했던 글이 `state/pending_full.json` 에 쌓여 있다. 이 명령이 답글을 받아 `raw/` 에 저장하고,
   답글이 실제로 잡힌 글만 `reanalyze` 로 출력한다. `reanalyze` 에 나온 글마다:
   - `raw/<글ID>.md` 를 읽고 3~5번을 **처음부터 다시** 한다. 본문만 보고 내린 판정은 무효로 취급한다.
   - 결과는 그 글의 원래 보고서(항목의 `report` 경로) 맨 아래 `## 재검토 (YYYY-MM-DD, 답글 반영)` 섹션으로 덧붙인다.
     원래 판정과 달라진 점을 첫 줄에 쓴다. 예: "지금 적용 → 보류. 4~7번을 보니 팀이 있어야 되는 방법".
   - `methods.md` 의 해당 줄을 갱신하고, 새 실행 과제가 생기면 오늘 보고서 실행 과제 표에도 넣는다.
   - `still_pending` 에 남은 글은 그대로 둔다. 로그인 만료 메시지가 보이면 대화 끝에 "`--login` 다시 필요" 한 줄.
   재검토 대기 글이 없으면 이 단계는 한 줄 출력으로 끝난다.

1. **새 글 목록 가져오기**
   ```bash
   python3 threads-watch/fetch_threads.py --mark
   ```
   `new_posts` 가 비면 "새 글 없음 (핸들, 시각 KST)" 한 줄로 끝낸다.

2. **본문 + 작성자 답글 전체 가져오기** (새 글마다)
   ```bash
   python3 threads-watch/fetch_thread_full.py <글 URL>
   ```
   로그인된 브라우저 프로필로 글 페이지를 열어 작성자 본인 답글까지 모아 `threads-watch/raw/<글ID>.md` 에 저장한다.
   이 채널들은 "본문 1~3개 + 나머지는 답글" 구조가 흔해서 **답글을 안 읽으면 메소드의 절반을 놓친다.**
   실패하면(로그인 만료, 클라우드 실행 등) 보고서에 "답글 미수집" 이라고 적고 본문만으로 진행한다. 그리고 **반드시** 대기 목록에 넣는다:
   ```bash
   python3 threads-watch/fetch_thread_full.py --add <글 URL> --reason "답글 미수집" --report threads-watch/reports/YYYY-MM-DD.md
   ```
   그래야 답글이 읽히는 날 0번 단계가 다시 분석한다. 본문이 번호 목록 도중에 끊긴 글은 판정 뒤에 "(답글 반영 전 임시)" 를 붙인다.

3. **글별 메소드 추출** (각 항목 1~3줄, 원문 표현 아닌 로빈님 말로 바꿔 쓴다)
   | 항목 | 내용 |
   |---|---|
   | 출처 | 인물·책·사례. 글쓴이의 해석인지 원전 인용인지 구분 |
   | 메소드 한 줄 | 이 글이 말하는 방법을 한 문장으로 |
   | 항목 정리 | 7가지면 7가지 전부. 답글에 있던 것도 포함 |
   | 원리 | 왜 통하는가. 손해 회피·시간 절약·신뢰 축적 등 근본 이유 |
   | 로빈님 상황 대조 | 이미 하고 있는 것 / 안 하고 있는 것 / 반대로 하고 있는 것 |
   | 적용 영역 | 위 사업 지도 코드 A~G 중 1~2개 |

4. **판정** (글마다 하나)
   - **지금 적용**: 이번 주 안에 행동으로 옮길 수 있고 비용이 낮다.
   - **보류·검토**: 방향은 맞지만 전제(팀, 자금, 시간)가 아직 없다. 무엇이 갖춰지면 하는지 적는다.
   - **해당 없음**: 로빈님 사업 구조와 안 맞거나 이미 충분히 하고 있다. 이유 1줄.

5. **실행 과제 작성** ("지금 적용" 글마다 1개, 많아도 하루 3개까지)
   - 형식: **무엇을 / 언제까지 / 어떻게 확인** 세 칸.
   - 예: "다음 공구 고정 댓글에 구매 전 막히는 지점 질문 1개 넣기 / 이번 주 업로드 / 댓글 답변 수와 내용으로 확인"
   - 추상어 금지. 로빈님이 읽고 바로 캘린더에 넣을 수 있는 문장으로.
   - 이미 로빈님 지침에 있는 원칙(단점 먼저, 정보 다큐 위장 등)과 겹치면 "이미 원칙에 있음, 실행 여부만 점검" 으로 처리.

6. **누적 관리**
   - `threads-watch/methods.md` 에 "지금 적용" 판정 메소드를 한 줄씩 누적한다 (날짜 · 출처 · 메소드 한 줄 · 적용 영역 · 과제 · 상태).
   - 같은 원리가 다른 인물·글로 3번 이상 나오면 보고서 맨 위 "반복 원리" 에 올린다. 여러 사람이 같은 말을 하면 그게 진짜 중요한 것이다.

7. **보고서 저장·전달**
   - `threads-watch/reports/YYYY-MM-DD.md`, 형식은 `report-template.md`.
   - `git add threads-watch && git commit -m "threads-watch: YYYY-MM-DD 메소드 보고서"` 후 현재 브랜치 push.
   - 대화에는 **재검토 결과(있으면) + 반복 원리(있으면) + 판정 표 + 실행 과제 전체** 만 붙인다. 글별 상세는 파일로.
   - `state/pending_full.json` 도 함께 커밋한다.

## 판단 기준 메모
- 글쓴이가 요약한 것은 원전과 다를 수 있다. 원전을 알면 한 줄로 바로잡는다. 모르면 "원전 미확인" 이라고 쓴다.
- 좋아요·조회수는 데이터에 없다. 반응을 추정해 쓰지 않는다.
- 자기계발 글은 뻔한 말이 많다. 뻔한 항목은 "해당 없음" 으로 빨리 넘기고, 로빈님 상황과 **어긋나는** 항목에 시간을 쓴다. 어긋남이 배움이다.
- 로그인된 브라우저는 로빈님 개인 계정으로 로빈님이 볼 수 있는 글을 하루 몇 건 읽는 용도다. 대량 수집·다른 용도로 쓰지 않는다.
